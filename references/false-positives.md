# False-positive discipline

An audit is judged by what it *doesn't* report as much as by what it does. A
report with forty findings, thirty of which are noise, gets skimmed once and
then ignored — and the six real issues die with it.

Apply this file after every hunting pass, before anything reaches the ledger as
`confirmed`.

---

## The gate

For each candidate, answer all four. A single "no" means it is not a confirmed
finding.

1. **Can I name the low-trust actor?** Not "an attacker" — *which* actor, with
   what starting access.
2. **Is the input actually attacker-controlled at this point in the path?** Trace
   it. Do not assume.
3. **Is the control genuinely absent or defeated here?** Check for validation
   upstream, framework-level defaults, and middleware. Most "missing checks" are
   checks that live one layer up.
4. **Can I state the concrete result?** A specific record, privilege, file, or
   outage. "Could lead to compromise" is not a result.

---

## Hard exclusions

Do not report these as vulnerabilities. Ever, unless the specific carve-out
applies.

### Trust and identity

1. **UUIDv4 and CSPRNG tokens are unguessable.** An attack requiring an attacker
   to guess one is not valid. *Carve-out:* the identifier is sequential, derived
   from a timestamp, generated by `Math.random`/`rand()`, or leaked elsewhere.
2. **Environment variables and CLI flags are trusted input.** Whoever sets them
   already controls the process. An "attack" premised on controlling `$PATH`,
   `NODE_ENV` or an argv value is not a finding. *Carve-out:* the value crosses
   a boundary — it lands in a container image layer, a CI log, or a
   world-readable file.
3. **Configuration files in the repository are trusted**, unless the finding is
   precisely that they contain a secret, or that they are writable by a
   lower-privileged actor at runtime.
4. **Admin-only functionality is not privilege escalation** for an admin. State
   which role is required; if the required role already has the capability, no
   boundary was crossed.

### Client-side code

5. **Missing authorization in client-side TypeScript/JavaScript is not a
   vulnerability.** The server is responsible for authorizing every request.
   Report the *server* gap, or report nothing.
6. **SSRF and path traversal do not apply to client-side code** (`.js`, `.ts`,
   `.jsx`, `.tsx` running in a browser). The browser's origin model, not your
   code, is the control.
7. **React, Vue, Angular and Svelte escape by default.** Do not report XSS in a
   component unless it uses `dangerouslySetInnerHTML`, `v-html`, `[innerHTML]`,
   `{@html}`, a `javascript:` URL sink, or an explicitly bypassed sanitizer.
8. **Secrets visible in a frontend bundle** are a finding only if they are
   actually secret. Publishable keys (Stripe `pk_`, Firebase web config, public
   analytics ids) are designed to be public.

### Denial of service and resources

9. **Do not report generic resource exhaustion** — unbounded loops, large
   allocations, missing pagination, recursive parsing — unless the target is a
   shared multi-tenant service *and* you can show a small input producing
   disproportionate cost. *Carve-out:* algorithmic complexity with a proven
   amplification factor, e.g. ReDoS with a demonstrated catastrophic backtrack.
10. **Missing rate limiting is a hardening note, not a vulnerability**, unless
    the endpoint performs authentication, sends money, or sends messages — where
    it enables credential stuffing or abuse with a nameable result.

### Language and platform

11. **Memory-safety findings only apply to memory-unsafe languages.** C, C++,
    Objective-C, unsafe Rust, unsafe C#, cgo. Do not report buffer overflows in
    Python, Java, Go, Ruby, or JavaScript.
12. **Do not report a "crash" as a vulnerability** without a boundary. A parser
    that throws on malformed input is behaving correctly in most contexts.
13. **Prototype pollution requires a reachable gadget.** Finding a merge function
    is not enough; name the property and what it changes.

### Cryptography

14. **MD5 and SHA-1 are not findings when used for non-security purposes** —
    cache keys, ETags, content addressing, deduplication, test fixtures. They
    *are* findings for password hashing, signatures, integrity verification, or
    token generation.
15. **`Math.random()` is only a finding when the value is security-relevant** —
    a token, nonce, session id, password reset code, or OTP. Not for jitter,
    sampling, shuffling a carousel, or generating test data.

### Files, docs and tests

16. **Documentation and markdown files are not attack surface.** Do not report a
    vulnerable code sample inside a README as a live vulnerability. Do report a
    real credential there.
17. **Test files, fixtures and mocks are excluded by default.** Hardcoded
    credentials in a test suite are only a finding if the credential is real and
    works against a real system.
18. **Generated and vendored code is out of scope** unless the finding is that a
    vulnerable version is bundled — which belongs to the dependency domain, not
    the code domain.

### Injection specifics

19. **Parameterised queries are not SQL injection**, even when the surrounding
    code builds a string — check whether the interpolated part is an identifier
    the ORM quotes, or a bound value.
20. **Command execution with a fixed argument array is not command injection.**
    `execFile('git', ['log', userInput])` does not invoke a shell. `exec('git log
    ' + userInput)` does. Know which one you are looking at.
21. **Path traversal requires the path to escape a root.** If the code calls
    `path.resolve` and then verifies the result is still inside the base
    directory, the control is present.

## Calibration

When you are genuinely uncertain:

- **Confidence below "firm" and you cannot trace the input?** → `needs-validation`,
  with the specific blocker.
- **Control might exist one layer up but you did not check?** → go and check.
  That is one file read, and it is the difference between a finding and an
  embarrassment.
- **Real defect but no attacker path?** → record as `info` with the honest note
  that it is defence in depth.

## Recording a rejection

Rejections are worth as much as findings, because they stop the next run from
re-raising the same noise:

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/finding.mjs" status <ID> rejected \
  --note "Bound parameter; the ORM quotes the identifier. Verified at src/db/query.ts:88."
```

The note must say *what you checked*, not just that you disagreed.
